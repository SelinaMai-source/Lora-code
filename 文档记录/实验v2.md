## 一、实验到底在做什么？自测什么？
这个实验是在做 Continual Instruction Tuning（持续指令微调）。核心场景是：同一个 Llama 3.1 8B Instruct 骨干模型按顺序接收一串不同任务 segment，每到一个新 segment 就用 LoRA 继续微调，然后立即评估模型在当前任务和已经见过的历史任务上的表现。
它自测的不是单个静态数据集上的一次性准确率，而是持续学习过程中的三个问题：新任务能不能学会，旧任务会不会忘，以及遇到任务切换时，方法里的漂移检测、LoRA bank、router 和 anti-overlap 机制是否真的在起作用。
- benchmark：主要是 instrdialog 和 instrdialog++ 两条 CITB 风格的持续任务流。
- 训练方式：每个 segment 训练 LoRA，然后评估当前 segment 以及所有已见 segment。
- 运行方式：真实大实验通过 tmux 后台跑，并把指标同步到 W&B project `lora-citb-acl`。

## 二、baselines 和 ours 分别是什么？
Baselines 是标准对照方法，用来回答“如果不用我们完整方法，普通持续 LoRA 或简单记忆/路由策略能做到什么水平”。
- Sequential：顺序 LoRA。所有任务按顺序继续训练同一个适配器，是最朴素的持续微调。
- Replay(10) / Replay(50)：LoRA 加 replay buffer，训练新任务时混入少量旧样本，测试 replay 对抗遗忘的作用。
- PeriodicLatest：周期性维护/切换 LoRA 适配器，使用最新或周期性策略作为对照。
- RouterOnly：主要测试路由器本身的分配能力，不包含完整方法的全部机制。
- BankNoRouter：有 LoRA bank，但不使用 router，用来拆分 bank 和 routing 的贡献。

Ours 是完整方法：漂移检测（drift detector）判断任务分布是否变化，LoRA bank 保存多个分支适配器，router 决定样本应该走哪个分支，anti-overlap 正则尝试让不同分支学到更分离的表示。消融实验会分别关掉 bank、drift、router、overlap，或扫 LoRA rank、branch 数、anchor size、overlap beta 等超参。

## 三、实验目标是什么？期望得到哪些指标和结果？
实验目标是证明 ours 在持续指令微调中比 baseline 更能兼顾新任务学习和旧任务保持。理想结果不是只看最后一个任务，而是整条任务流上的综合表现。
- eval.current_score：当前 segment 的准确率/任务分数。希望越高越好。
- eval.seen_avg_score / eval.anytime_score：所有已见任务的平均表现。希望越高越好，这是持续学习最核心指标。
- eval.forgetting：历史任务遗忘程度。希望越低越好。
- token_f1_mean、lcs_overlap_mean：生成文本与答案的软匹配指标。希望在 exact score 低时能辅助判断是否只是格式不匹配。
- routing.oracle_agreement_rate、decision_confidence、utilization_entropy：判断 router 是否真的学会合理分配分支。
- drift.false_alarm_rate、drift.miss_rate、detection_delay_mean：判断漂移检测是否及时且准确。

期望结果是：ours_full 的 seen_avg_score / anytime_score 高于 baselines，forgetting 更低；消融中去掉关键模块后性能下降；drift miss rate 不能太高，router 不能完全退化成随机或单一分支。

## 四、实验具体设计细节
实验按 segment 顺序运行。每个 segment 代表一个任务或一组同分布指令样本。训练阶段只使用当前 segment 的训练样本，某些 baseline 或 ours 会额外使用 replay buffer、LoRA bank 或 router。评估阶段会在当前 segment 和所有已见历史 segment 上重新计算指标，因此可以同时观察新任务学习能力和历史任务保持能力。

核心评估指标与含义：
- EM / exact match：最严格的答案匹配指标。生成答案经过归一化后必须与 gold answer 完全一致才计为正确。表里的 eval.current_score、eval.seen_avg_score 在多数分类/短答案任务上可以近似理解为 EM/任务准确率。
- current_score：当前 segment 上的 EM/任务分数。它回答“刚学的新任务有没有学会”。
- seen_avg_score：对所有已经见过的 segment 求平均后的 EM/任务分数。它回答“模型到目前为止整体还保留了多少能力”。
- anytime_score：训练过程中到当前时间点的历史平均表现，和 seen_avg_score 一起衡量持续学习质量。
- forgetting：历史任务曾经达到的最好分数与当前分数之间的差。越高代表忘得越严重，越低越好。
- token_f1_mean：按 token 计算预测与 gold 的 F1。它比 EM 宽松，能发现“答案部分相关但没有完全匹配”的情况。
- lcs_overlap_mean：最长公共子序列重叠度，也是一种软匹配指标。它能辅助判断模型是否生成了相似文本但格式或边界不一致。

路由、漂移和分支相关指标：
- routing.oracle_agreement_rate：router 选择的分支与 oracle 最优分支的一致率。越高说明 router 越接近理想分配。
- drift.miss_rate：真实发生任务变化但未检测到的比例。越低越好；目前已有结果中这个值偏高，是重点风险。

## 六、已经产出的结果有什么明显问题？

从上述 v2 数据可以看出，目前结果仍存在以下明显问题：

1. **Ours Full 表现不佳**：
   - `Ours (Full)` 的 `seen_avg_score` 仅为 0.0053，遗忘率 `forgetting` 高达 0.3491。
   - 相比之下，`Ours (No Overlap)` 的 `seen_avg_score` 达到了 0.2675，遗忘率仅为 0.1444。这说明当前的 `anti-overlap` 机制可能对模型性能产生了严重的负面影响，导致模型无法有效学习或保持知识。

2. **Drift Detector 漏检率依然很高**：
   - `Ours (Full)` 的 `drift.miss_rate` 为 0.9444，`Ours (No Overlap)` 和 `Ours (No Router)` 的漏检率也高达 0.8889。
   - 极高的漏检率意味着任务发生变化时，漂移检测器未能及时发现，导致未能创建新的分支（`Ours Full` 仅创建了 2 个分支，而 `No Overlap` 创建了 3 个分支），从而严重影响了后续的路由和学习。

3. **Current Score 普遍为 0**：
   - 所有方法的 `eval.current_score` 均为 0.0000。这表明模型在刚学完新任务时，依然无法在当前任务上取得 Exact Match 分数。尽管 `token_f1_mean` 和 `lcs_overlap_mean` 有一定数值（例如 `PeriodicLatest` 的 `token_f1_mean` 为 0.3472），说明模型生成了部分相关文本，但精确匹配依然失败。

4. **Baseline 表现反常**：
   - `PeriodicLatest` (0.2623) 和 `BankNoRouter` (0.2263) 的表现远好于 `Ours Full` (0.0053)。这进一步说明我们完整方法中的某些机制（如 overlap penalty 和 drift detection）可能起到了反作用。

## 七、针对近期分数低与漏检问题的改动及后续建议

虽然我们在 v1 阶段进行了 EM 提取修复和漂移检测调优，但 v2 结果显示问题依然存在。后续建议：

1. **排查 Anti-Overlap 机制**：
   - 鉴于 `Ours (No Overlap)` 表现大幅优于 `Ours (Full)`，需要重点检查 anti-overlap 的 loss 计算、beta 权重设置是否过大，导致破坏了模型原本的表示能力。

2. **继续调优 Drift Detector**：
   - `miss_rate` 依然在 90% 左右，说明之前的改动并未彻底解决问题。可能需要重新审视 NLL 偏移的计算方式，或者引入更敏感的统计检验方法。

3. **深入分析 Current Score 为 0 的原因**：
   - 尽管放宽了评估标准，当前任务的 EM 依然为 0。需要抽样查看 v2 的预测文本与 gold 答案，确认是否仍有格式对齐问题，或者模型在单 segment 训练时出现了欠拟合/过拟合。
